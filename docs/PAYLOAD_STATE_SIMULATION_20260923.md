## 已落地的链路

C++ Gazebo 世界观察器核对独立仓库和机器人基线，生成实际采集、完整且带版本的 EMPTY；
C++ 账本通过独立 MoveIt `GetPlanningScene` 回查确认，C++ 几何消费者接收同一附件版本。
源策略为 `static_world_empty_only_v1`，只适用于当前受限的静态背景仓库。

观察器检查全部 53 个模型、插件、机器人 link/joint 结构和外部关节。新增静态物体也拒绝，
因为既有适配层可能通过移动静态物体模拟附着。未知/附件插件、动态物体、缺失或变动的基线
不能当成空载。有载来源尚未实现；没有降低碰撞、几何、持有授权或六消费者确认门槛。

新 C++ 加载入口查出真实 World entity ID，再提交插件加载；它拒绝共享默认域和重复加载。
加载“已受理”与实际观察器就绪分开。Supervisor 新增显式 `--payload-source-id` 转发会话和
账本日志参数；共享 install 未覆盖，构建和安装均在本轮隔离目录。

## 本轮发现并修复

1. **热加载边界。** 仅按世界名称提交时，接口已受理但传入 Configure 的实体无效。首轮试载
   导致 Gazebo 退出，失败证据保留。加载器改为查实际 entity ID；Configure 捕获配置异常，
   文件路径与身份字符串分开校验。后续正常加载成功。
2. **假 EMPTY 边界。** 不能豁免机器人任意后代模型，也不能仅按 link 数量判断。增加独立
   机器人描述的 link/joint 集合和连接端点核对；额外嵌套模型拒绝。
3. **采集与 `/clock` 到达顺序。** 第一份 8 秒记录有 17/146 条消息比接收端 ROS 时钟提前
   1–2 ms。增加单帧有界发布缓存后，另一份 8 秒记录中 140 条均无未来时间，采集龄期约
   48–50 ms；原始采集时间与截止时间未修改。该结果是协议时序观察，不是性能负载验收。
4. **故障恢复活锁。** 真实场景不一致解除后，账本已确认，几何却一直要求新采集。根因是每次
   合法旧采集被拒绝都会把恢复界限推到新的接收时间。修复只冻结这类重试的界限；真实负向
   证据继续撤销并更新边界。旧代码在 C++ 用例及带 50 ms 采集延迟的 ROS 用例中复现失败，
   新代码及实际仿真复测通过。

## 下一阶段开始前的逻辑复核

已复核 `kinematic_payload.cpp`：当前 JSON 状态只有 applied command、attached、跟随误差、
实际/目标位姿和采集时间，缺少实例 epoch、完整资源身份、pending 状态及全量物体清单。
因此不能把现有单物体 JSON 接到 EMPTY 来源上就宣称满足完整附件契约。

下一实现采用 C++：KinematicPayload 在实际 PreUpdate/PostUpdate 中写入版本化的 ECM
执行证据组件；世界观察器枚举所有物体及对应插件，核对注册清单，再生成全量
AttachmentObservation。组件至少包含插件/对象 epoch、accepted/applied 命令、待决标志、
父模型/link、固定偏置、实际/期望位姿、采集双时间和明确错误。现有 JSON 可保留作诊断兼容，
不直接作为授权输入。插件重启、对象增删、父 link 变更均必须产生新版本或撤销。

| 边界 | 所需行为 / 验证 |
|---|---|
| 启动无状态 / 新增未登记对象 | UNKNOWN，不能由空数组推断 EMPTY |
| 请求已排队但未实际施加 | TRANSITION，accepted 不代替 applied |
| 实际附着与稳定跟随 | 对齐物理 link→TCP 固定变换，并验证同采集的位姿残差后给出 ATTACHED |
| 释放已请求但未完成 | 保留过渡状态；实际完整清单与独立 MoveIt 回查一致后才给出 EMPTY |
| 父 link 丢失、模型删除、插件重启 | 立即撤销；重建后的实体不能沿用旧 epoch |
| 箱体/圆柱/球体/mesh、偏置载荷 | 几何、质量和变换绑定相同版本；缺数据或无法保守包络则拒绝 |
| 左右分别载荷 / 双手共持一物 | 全量清单去重，单物体一个主父 link；额外共持约束单独核对，不能重复计算质量 |
| ROS 时钟暂停/回退、乱序/ABA | 双时间过期，拒绝旧版本；新采集和重新回查后才能恢复 |

资源链复核发现现有原生 task arbiter 的 Ownership 明确仅管导航 action，不是整机资源总线；
不能把该 goal ID 直接包装成机械臂租约。既有 Python hold 发布也不能替代新 C++ 核心要求的
正式资源授予与任务保持动作终态。后续授权适配必须由实际资源所有者和执行器提供证据，
六消费者正向验证排在此后。此段是实现准备，尚未写成已实现能力。
