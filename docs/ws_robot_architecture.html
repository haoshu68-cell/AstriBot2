01

包的分工

十二个自研包 + 两个 vendored 包。色标表示这个包跑在仿真侧还是实机侧——这条分界几乎贯穿本栈的每一个问题。

包侧负责
astribot_s1_description通用模型的唯一来源。顶层 urdf/astribot_s1.xacro 包含 7 个子 xacro，展开为 33 关节 / 34 link；同时承载 ros2_control 与 Gazebo 插件宏。
astribot_s1_gazebo_bringup仅仿真世界、spawn、8 个控制器、parameter_bridge、静态 TF 别名、rviz。
astribot_s1_perception通用8 个节点。雷达预处理与融合（仿真侧）、点云→栅格与 map→odom 分解（实机侧）、slam_toolbox 封装、地图源选择。
astribot_s1_autonomy通用4 个 C++ 可执行。自滤 + 多层高度切片→LaserScan；前沿搜索；探索协调状态机；Livox CustomMsg 转换。
astribot_s1_navigation通用Nav2 集成层：顶层 launch、两份 nav2_params_*.yaml、行为树、4 个适配/诊断节点，以及 explore_metrics 纯函数度量库。
astribot_s1_path_tracking通用一个 nav2_core::Controller 插件 ThreePhaseController，它把 MPPI 嵌在自己内部。
astribot_s1_dynamics_coupling通用一个 Twist→Twist 节点，按手臂伸展程度压底盘速度。
astribot_s1_chassis_effort_drive仅仿真全向逆解 + 每轮 PID + 摩擦前馈 → 四路力矩。完全不碰 SDK。
astribot_trajectory_bridge仅实机全仓唯一调用厂商 SDK 的地方。手臂/底盘/夹爪指令桥、只读状态与里程计桥、写通路门禁。
astribot_bridge_msgs仅实机BridgeStatus（28 个状态码）+ DispatchWaypoints + SetGripper。
astribot_s1_moveit_config通用SRDF（7 个规划组）、运动学、关节限位、OMPL 配置、控制器映射、move_group launch。
astribot_s1_manipulation通用规划能力：注册 6 个 allocator 的 OMPL planner-manager 插件、闭链投影、碰撞/奇异校验、轨迹时间优化。
一处循环依赖，靠构建期性质化解

moveit_config 依赖 manipulation（它要那个 planner 插件），而 manipulation 的 launch 又 include moveit_config 的 launch 并读它四份配置。这个环只存在于 launch / 运行期——moveit_config 是纯配置 CMake 包，它的 CMake 只做 install，所以编译期没有环。

02

两条启动链

同一套栈，两种串行方式：仿真在一个 launch 文件里靠进程退出事件串，实机在八个 shell 阶段里靠实测话题拍率串。

仿真：单 launch 文件内的事件链

warehouse_sim.launch.py 返回的动作顺序是有意义的，其中只有一条硬依赖链用 RegisterEventHandler 表达：

SetEnvironmentVariable ROS_LOCALHOST_ONLY=1 / IGN_IP / GZ_IP / ROS_DOMAIN_ID=25 │ （必须最先 —— 之后每个 Node 都继承它） ├─ gz_sim ────────────────────── ros_gz_sim/gz_sim.launch.py ├─ robot_state_publisher ─────── 现场展开 xacro → /robot_description ├─ spawn_robot ───────────────── ros_gz_sim/create -topic robot_description │ └─ OnProcessExit ──▶ controllers_spawner （单进程，8 个控制器） │ └─ OnProcessExit ──▶ omni_effort_drive_node ├─ parameter_bridge ──────────── 5 路：/clock、/odom、/tf、2× 雷达、相机 ├─ 3× static_transform_publisher 给 gz 那串长 frame_id 做零变换别名 └─ rviz2

两个细节是承重的。控制器 spawner 是一个进程带全部 8 个控制器名，因为并行 spawner 会间歇性地在 load_controller/configure_controller 上抢；另外 effort-drive 的 include 必须显式传 params_file——LaunchConfiguration 是共享上下文而非按 include 作用域，否则延迟 include 会捡到外层某个节点先占下的那份 yaml（曾因此让 pid_kp 变成 2.0 而自旋 3.3 rad/s）。

实机：八个阶段，每阶段等实测拍率

tools/robot/bringup_stages.sh。每一阶段等的是真实发布拍率，不是进程存在——「进程活着但 0 Hz」在这台机器上反复出现过。因为厂商裁剪过的 ros2 CLI 没有 launch 子命令，脚本用自带的 $RL launcher；SDK 那个控制权 stdin 提示由 answer_sdk_prompt 处理。

感知到地图

两条完全不同的上游，汇到同样的两个下游契约：一份 /scan 给 costmap，一份 /map 给 planner。这一节的分叉点就是整个仿真/实机分界的物理位置。

livox_fusion_node仿真message_filters 同步两路（sync_slop_sec 0.05），统一变换到 astribot_torso_base。

切片链：自滤先于切片

pointcloud_slice_scan_node（autonomy 包）是这条链上最容易被误解的一环。它订阅 input_cloud_topic（yaml 里是 /livox/fused_points），先做自滤——足迹圆柱 + 每个 link 的胶囊体，再做四层高度切片，出 /scan_from_cloud 与 /livox/cloud_self_filtered。

自滤是硬要求而不是优化：夹爪一度整个不在自滤链里，机器人把自己的指尖当障碍，表现为 planner 报 Starting point in lethal space、探索 0 次派发。scan_guard_policy.hpp 单独持有 TF 查询预算与 hold_last 的上限——感知陈旧必须显式失败，不能静默沿用上一帧。

04

探索状态机

autonomy 包里有两个会算前沿的东西，但只有一个能派发目标。这一点搞混过一次，代价是两个派发方互相抢占 Nav2 的单目标 action。

节点会算前沿会派发目标会发速度
frontier_explorer_node是（每 2.0 s）否 —— 无 Nav2 客户端否
exploration_coordinator_node是（自带一份 FrontierSearch）是，唯一是（仅两个状态）

frontier_explorer_node 是纯建议者：订 /map，往 /explore/goal_pose、/explore/status、/explore/complete 发结果，没有 action 客户端也不发速度。协调器不消费 /explore/goal_pose——它有自己内嵌的前沿搜索。所以这两个节点绝不能同时跑：那会变成两个独立源朝同一个单目标 action 塞目标，而 Nav2 的重发即抢占，旧目标以失败回来，失败又触发重试，自激。

协调器的九个状态

kBootstrap

三个谓词把「谁在开车」这件事变成可判定的：allowsGoalGeneration()、hasActiveNavGoal()、drivesChassisDirectly()——最后这个只对 BOOTSTRAP 与 ESCAPE 返回真（橙色两格）。其他任何状态下 /cmd_vel_nav_body_raw 上出现非零帧，就说明有别的东西在发，这是排查的第一个判据。

职责拆分

failure_budget.cpp
两个互相独立的预算：sample_failures 与 validation_failures。清零要求真的离开那个循环——只有 onGoalDispatched() 才清 validate 那本账。计「连续失败」而不是「尝试次数」：把成功也计进去会误杀那种沿途多处窄但整体走得通的长路径（实测 13 次接管 10 次成功却被判「不可行」）。
escape_logic.cpp
evaluateEscapeTrigger / segmentPhysicallyClear / pickBreadcrumbTarget / findNearestPlannableCell / escapeVelocity / escapeCleared。
path_validator.cpp
目标净空 + 沿插值路径采样，fail-closed：拿不到数据就判不可行。
costmap_adapter.cpp
把 nav2 的 0–255 折成三态；1–252 那段膨胀梯度被有意拍平成「自由」——这一层要判的是「能不能站」，不是「贵不贵」。

校验必须与规划器同图

05

Nav2 与三相控制

navigation 包是纯 Python，不含一行 C++；真正的控制律在 path_tracking 包里，是一个把 MPPI 嵌在自己内部的 nav2 插件。这一节讲这两者的接缝。

navigation 起哪些进程

nav2_full_bringup.launch.py 是顶层入口，动作顺序有意义：(0) 先 SetLaunchConfiguration('nav2_rviz_flag', use_rviz) 快照，(1) include perception_slam_bringup.launch.py 并把 autonomous_patrol:='false'、use_rviz:='false' 钉死，(2) scan_source=='slice_scan' 时用 GroupAction(scoped=True) 起切片节点，(3) navigation.launch.py，(4) 探索协调器，(5) rviz2。

navigation.launch.py 起 7 个受生命周期管理的节点（controller_server、smoother_server、planner_server、behavior_server、bt_navigator、waypoint_follower、velocity_smoother）+ lifecycle_manager_navigation（autostart:=true），再加三个非生命周期节点 cmd_vel_body_to_world_node、arm_speed_limiter_node、条件性的 arm_chassis_coupling.launch.py。刻意没有 map_server 与 amcl——/map 与 map→odom 都由 SLAM 侧提供。

两个 launch 层面的静默失效

launch_arguments 白名单漏项不报错、不告警，子 launch 直接用自己的默认值。nav2_full_bringup 曾同时漏掉 max_linear_speed（导致限速扫描各档位数字完全一样）与 enable_posture_monitor（实机上根本关不掉那个会永久归零 /cmd_vel 的开关）。

RewrittenYaml 只能改标量。max_linear_speed 按键名改写 vx_max/vx_min，vy_max/vy_min 钉死 '0.0'；而 velocity_smoother 的 max_velocity/min_velocity 是双精度数组，刻意不改写——RewrittenYaml.convert() 只试 int/float/bool，数组会被字符串化，configure 期类型报错，结果是 nav2 永不 activate 而 9 个进程全都活着。

跟踪朝向在 ±57° 死区内没有梯度

PathAngleCritic 是死区型，TwirlingCritic(10.0) 还在反向压制，PathAlign(14.0) 只管位置且能被横移满足。所以原地转向只来自四个与 vy 无关的离散触发（实测 27 次 / 18 轮）。想靠调权重让它「主动转身对齐」是没有着力点的。

度量与诊断

explore_metrics/ 是纯函数库，唯一的判据出口在 round_metrics.py：geometry.py（cross_track_distances 按 2048 分块、traveled_length 带 0.002 m 步长门、heading_tangent_errors 按 0.20 m 抽稀切线）、signals.py（rate_from_stamps 报中位间隔的倒数并强制带 p95）、scan_metrics.py（valid_mask 把 0 当无效而非「贴脸」）、plan_status.py（失败率只数 ABORTED）、state_parse.py（按第一个 = 切分）。命名上一律带 xxx_proxy 后缀，且 None 永不当 0。

path_tracking_diagnostics_node.py 同时监视四个转发跳，因为链上任何一处断掉的现象完全相同——机器人不动。arm_speed_limiter_node 出 /speed_limit（nav2_msgs/SpeedLimit）给 velocity_smoother，其 extended_reach_m 0.64 = costmap 半径 0.42 + 支撑多边形距离 0.2163；这一层与 dynamics_coupling 的缩放是串联相乘的。

06

cmd_vel 链

从控制器算出的速度到轮上的力矩，要过五个进程、四次话题转发。这条链是本仓最常出问题的地方，因为任何一跳断掉的现象都一样：机器人不动。

omni_effort_drive_node

仅仿真，respawn=True。订 /cmd_vel + /joint_states，发 /wheel_effort_controller/commands（顺序 [RF, LF, RR, LR]）与每轮调试话题。逆解是 ω_i = global_sign · (1/r) · (c_vx·vx + c_vy·vy + c_wz·wz)，系数从轮关节的 rpy 推出——45° 斜置轴，X 型全向，不是麦轮；c_wz 里已经含了那约 0.30 m 的力臂。每轮 PID（kp=0.4, ki=0.1, kd=0.0）+ 库伦/粘性摩擦前馈（0.1 / 1.0）+ ±15 N·m 限幅 + 抗积分饱和。

写通路门禁

write_gate.py 的 evaluate_write_gate(...) 拒绝顺序是固定的，每一条对应一个 BridgeStatus 码：

target 不在 ('sim','real') 里 → TARGET_MISMATCH 后端数 == 0 → SDK_NOT_ALIVE 后端数 > 1 → MULTIPLE_BACKENDS 实测后端 ≠ 声明后端 → TARGET_MISMATCH real 且无 allow_write_to_real → REAL_WRITE_NOT_AUTHORIZED real 且 robot_mode != 'safe' → ROBOT_MODE_UNEXPECTED 声明 sim 但实测是 real → TARGET_MISMATCH 另：validate_pose_source_target_combo() → POSE_SOURCE_INVALID

allow_write_to_real 不出现在任何 yaml 里，只能命令行传。被拒时节点照常存活并继续上报，读通路完全不受影响——这样「为什么不动」永远有诊断信息可看。

铁律

每次使能真机写通路前必须先向用户确认。技术前置（/cmd_vel 无帧、电量足、leash 生效）不构成授权。另：SDK 那个控制权提示只发回车，绝不发 yes——yes 会立刻停止机器人运动。

回调分组：一个 250 Hz 内环能把订阅饿死

callback_layout.py 单独成一个模块，CHASSIS_GROUPS=('inner','outer','srv','cmd')、ARM_GROUPS=('exec','srv','grip')、THREAD_HEADROOM=2、executor_thread_count()；它刻意既不 import rclpy 也不 import 任何消息类型，就为了能纯逻辑地测。

它存在的原因是 2026-08-31 那次实机故障：4 个互斥回调组对 6 个 executor 线程，_on_cmd_vel 一次都没执行到。_last_twist 恒为 (0,0,0)，于是 leash（偏差 0）与看门狗（_last_twist_time is None）两个都不报，全程唯一可观测的异常只有 LOOP_OVERRUN。互斥组数量是 executor 线程数的下限——只拆组不加线程等于没改。

写通路的一拍

/cmd_vel + /scan（必须 qos_profile_sensor_data） └─ 250 Hz 内环 tick： 看门狗超时 → 归零 /scan 龄期联锁 → 归零 clamp_velocity slew_limit_velocity(dt) ← dt 是 measure_tick_dt 的实测值 to_local_velocity integrate_step_dt ← 底盘是位置接口 外环 SLAM 校正（可关） check_leash（与 SDK 实测位置比） session.set_joints_position

max_tick_dt_sec 0.04 的依据是算术：单拍最多推 0.04 m，远小于 leash_xy_m 0.25。用实测 dt 而不是 1/freq，是因为底盘走位置接口——拍慢了而 dt 按名义值算，位置指令就落在机器人后面。节点默认 disabled（start_disabled: true）。

手臂侧起两个 FollowJointTrajectory action server，以 250 Hz 流式下发，参数 control_way='direct', use_wbc=False, add_default_torso=False——SDK 默认 add_default_torso=True 会连躯干一起动。ArmTrajExecutor 相位 IDLE→STREAMING→SETTLING→DONE，取消后进 HOLDING。

保持位置必须持续重发

set_joints_position 发一次抓不住正在运动的关节（取消后漂 0.045~0.37 rad，持续重发才 0.0000）。SDK 自报的 desired 已经等于所发值却仍会漂，所以只能看实际位置。夹爪同理：中间开度单次下发会冲到全闭合（下发 cmd=50，0.5 s 内到 99.998）。

模型、规划组、规划器能力三件事分在三个包里：几何在 description、组与限位在 moveit_config、算法能力在 manipulation。

运动学树：为什么 dual_arm 只有 14 个关节

astribot_torso_base ├─ wheel_{RF,LF,RR,LR} ← 4 个全向轮 ├─ livox_mid360_{left,right} ← 2 个雷达 └─ astribot_torso_link_1..4 ← 4 自由度躯干链 └─ astribot_torso_end_effector ├─ astribot_head_link_1..2 → camera_link ├─ astribot_arm_left_base → link_1..7 → tcp_link → gripper └─ astribot_arm_right_base → link_1..7 → tcp_link → gripper

两条手臂的 base 都固定在 astribot_torso_end_effector，也就是那条 4 自由度躯干链的末端。躯干一动，两条手臂的基座跟着动——这正是 dual_arm 组里只含 14 个手臂关节的原因，另有一个 18 关节的 dual_arm_with_torso 组用于需要躯干参与的场合。

TCP 就坐在腕部碰撞球心上

tcp_link 沿 −y 离法兰 0.15 m（厂商的 effector_to_tool_pose），自身没有碰撞几何，但它与 link_7 那个 r=0.05 的球原点完全重合。于是「TCP 贴着物体」必然判碰撞，而它报出的 RETRIES_EXHAUSTED 与「被奇异否掉」是同一个错误码。夹爪的碰撞模型也曾整个缺失（腕部只有 r=0.05 而厂商包络伸到 −0.1997，沿抓取方向少 0.15 m），所有旧的抓取余量数字都已作废。

manipulation 的四个能力

闭链双臂规划 · planClosedChain()

captureRelativePose() 记下当前的 T_rel └─ OMPL 只规划 leader（7 自由度） └─ densify() max_joint_step 0.05，≤400 点 └─ 逐点 projectFollower() IK └─ 逐点校验：残差 / 碰撞 / 奇异 └─ 合成 14 自由度 → TOTG 时间参数化 └─ 对最终轨迹重新校验闭链残差 （TOTG 会重采样，前面的校验不算数）

误差定义 E = T_L⁻¹·T_R·T_rel⁻¹，position_tolerance 0.005 与 orientation_tolerance 0.02 分开判、绝不相加。返回值上 kAlreadyAtGoal 要求调用方同时测 !succeeded() && !noActionNeeded()。

奇异监视 · singularity_monitor

三个判据任一触发即否：min_singular_value < 0.02、condition_number > 80.0、σ_max < 1e-9。allow_singular_start: true 豁免第一个非奇异点之前的所有路点——因为路点 0 就是当前测得的位置，不是目标。这一条同时也是「越限起点必须留恢复通路」的实现：每个路点都查限位而路点 0 是测量值，机器人一旦越限就会每条轨迹都被拒、连开回来都不行。

OMPL 规划器扩展 · ompl_planner_extension

把 astribot_s1_manipulation/OmplPlannerExtension 注册成 planning_interface::PlannerManager，加 6 个 allocator（BITstar、InformedRRTstar、ABITstar、AITstar、SORRTstar，并覆盖 RRTstar），把可用规划器从 25 个补到 30 个。扩展键 optimization_budget_sec 与 goal_state_wait_sec 由 header-only 的 OptimizingPlannerWrapper 承接。

这个扩展存在的三条理由，每条都是踩过的坑

Humble 的 MoveIt2 本来没有 BIT*/Informed RRT*：其 OMPL 插件只注册 25 个规划器，yaml 里写一个未注册的名字会静默回落到组默认——「在跑 BIT*」实际可能是 RRTConnect。

informed 类规划器必须 planning_attempts=1：>1 会走 ParallelPlan，informed sampler 在 lazy goal 线程给出状态之前就抛，而 MoveIt 只报一句 Unable to solve the planning problem。

优化型规划器一定烧完全部预算：检测首解要看 "best cost REAL" 这个 progress property，pdef->hasExactSolution() 不行。所谓「BIT* 快 14 倍」其实是 optimization_budget_sec 配置差异；同样停在首解时它真正的优势是首解节拍好 32%。

轨迹时间优化 · trajectory_time_optimizer

IPTP@0.30 作基线 vs TOTG@0.90，再由 trajectory_metrics::evaluateTrajectory 独立复核。基线本身就违限时报 kJointLimitViolation 且不产出任何轨迹。

控制器映射与两个 mimic 陷阱

moveit_controllers.yaml 用 MoveItSimpleControllerManager 管 5 个 FollowJointTrajectory 控制器（夹爪只列 joint_L1 一个主动关节）。dual_arm 跨两个控制器 → 并行下发，同步性没有硬保证。

两个 mimic 陷阱

setJointGroupPositions 漏掉组外的 mimic 关节：SRDF 夹爪组只含主动关节，从动关节全不动，张口被静默算成一半、抓取角错一倍且零报错。要用 setJointPositions。

Gazebo 的 mimic 支持但不精确：有 7.8° 稳态误差（从动关节到 0.794 而不是 0.93）。看 /joint_states 永远发现不了，得反解从动关节角度。

为什么有一份 joint_limits.yaml

URDF 里没有加速度限位，所以这份文件只为补加速度而存在：a_max = v_max / 0.35 s，文件里已标明这是估计值而非厂商数据。description 包侧有 test_joint_limits_parity.py 校验两边一致。config/collision_overrides.yaml 是可追溯性记录，代码不读它；SRDF 里的 42 条 disable_collisions 才是生效的那份。

09

贯穿全栈的不变量

这些不是巧合，是同一条设计原则在十几处的具体实现。读代码时如果看到某处违反了它们，那处大概率是缺陷而不是特例。

一 · 「没有数据」与「数据是好的」必须分开，且朝保守侧退化

位置缺数据时
omni_effort_drive/joint_states 陈旧 → 全零力矩 + PID 复位
arm_chassis_couplingTF 从未成功 → activity 记 1.0（按完全伸出算）
state_bridge连续 25 次读失败 → 进程退出，绝不发陈旧值
path_validatorfail-closed：拿不到就判不可行
explore_metrics返回 None，绝不返回 0
slam_adapter契约违反 → 非零退出
chassis 内环/scan 超龄联锁 → 速度归零

二 · 读数必须自带龄期或 live 标记

一天之内栽过三次：陈旧 TF、冻结的拍率计数、把脉冲平均当速率。lookup_transform(..., Time()) 取「最新可用」——而 tf2 的 buffer 只在该 frame 对有新数据进来时才裁剪过期项，一条再也不更新的边，它最后那一帧会永久留在 buffer 里被当成「最新」返回。实测过一个节点以 20 Hz 稳定发布 13 小时前的 map→odom，自报「缺失 odom=25」看着完全健康。统计窗口也要随状态重开：enable 时漏清 _tick_first_time 会把 65 拍报成 165 Hz。

三 · 判据的几何必须逐字等于它声称测的那个边界

膨胀图 + 足迹多边形 = 底盘算两遍：253 只能用于中心格，多边形必须用 254。否则窄于 4× 侧向半宽（本机 1.58 m）的通道恒 253、零梯度；实测读数「51 次 253 : 2 次 254」就是这个错误的特征。同类的还有：方框当圆算（角上差 0.636 m）、检查半径 0.45 用在承诺 0.25 的节点上（在真墙 0.447 m 处必假阳性）。

四 · 单阈值门限必在边界自激

切入切出复用同一个 yaw_gate=0.120 的后果实测过：重新对齐 749 次、30 s 一步未前进、最后被硬超时踢回去，现象是「能进不能出」。修法是加 yaw_resume=0.06 + 锁存位 + 启动守卫。同理迟滞两侧必须同源同几何——切入看前视 1.0 m 而切出只看当前位姿，123 次切换的中位驻留 0.15 s 恰好 = 3 拍/20 Hz，即每次都在最早的合法拍就复原。

这两个数字来自已删除的层

yaw_gate / yaw_resume 出自窄通道接管层，该层已于 2026-09-07 整体删除——不要去代码里找。留在这里是因为教训与那一层无关：任何单阈值的进入/退出门限都会在边界自激。

五 · 入口判据不能当成每拍的驾驶判据

某一层用自己的进展来吊销自己的授权（1.5 s 的判据 vs 转正需要 3.93 s），同一个函数有三个泄漏口。判「谁在开车」要数超出本层硬上限的帧数，门限用旋转不变的模长 sqrt(0.10² + 0.05²) = 0.1118——用 |vx| > 0.10 是错的，横向分量能合法顶到 0.1118。

六 · 重试上限数「连续失败」，不数「尝试次数」

把成功也计进去会误杀那种沿途多处窄但整体走得通的长路径（实测 13 次接管 10 次成功却被判「不可行」）。且异常会以 20 Hz 重复抛——15 条就能把真正的告警淹掉。

七 · 存活信号不能藏在 early-return 之后

续租写在下层、上层接管就跳过，于是恰好在最需要时停租。看门狗除了续租还需要：回读龄期 + 连续 N 次回读（在回调里数）+ 一个算术下界。

八 · 成功判据必须显式枚举失败词

只 grep packages finished 让 8 笔提交全报 ✅，而每一笔都有 1 failed + 1 aborted + 2 not processed。colcon test-result 还会把跨轮次的陈旧 XML 一起算进来。另一个同类：模块级 pytest.importorskip 在 pytest 6.2.5 下会吃掉整个 collection——「干净的 1 skipped」比报错更危险（实测 430 条测试静默消失，修好后 501 passed）。

最后一条，也是最贵的一条

断言根因前，先跑那条能证伪它的命令。本项目已犯两次（「188% 饿不死 28 核」、「ldd 全部解析成功」）。错根因会扩散进文档、并让排查停止。相关的还有：验证机器人真的动了，不只是指令对——e2e 只比 dispatched_cmd 等于只验证了自己，「要求半开而 actual=99.998」曾因此被判通过。以及测试会把它本该抓的 bug 锁死：守卫、测试、yaml 注释三处写同一个错理由，那是一份证据而不是三份，变异测试救不了共享的错前提。

autonomy/README.md 的离地高度换算全部差 34 mm

已核对 · 文档

ws_robot/src/astribot_s1_autonomy/README.md:23 写地面 ≈ z = −0.129，引的是静态位姿里的 0.1292。但 docs/slam_nav_dataflow_and_datum.md 从 URDF 推出的是 −0.095（轮 joint z −0.015 − 球半径 0.08，且球心偏移经 joint 的 rpy 旋转后对 z 的贡献恰好为 0），并有点云地面拟合独立佐证（0.1745 − 0.082 = 0.093）。
