## 数据链与实现

Gazebo 全量附件清单 → 载荷账本与独立 PlanningScene 回查 → GeometryState → A2 正式 C++ HoldResources 执行器 → SetFixedEnvelope → 全局/局部代价图、规划、控制、策略、独立保护六消费者 → 同 session/epoch/hash 确认后允许导航。

规划器和控制器在真实 Costmap2DROS 上回读实际轮廓，分别回报自身及其代价图确认；策略和独立保护应用自己的多边形后回报。收到服务的 accepted 只表示提案进入握手，不能当作放行。本次没有伪造实际导航域的正向保持或 ACK，也没有发送底盘运动目标。

两处 C++ 修复：

1. **切断确认反馈循环。** 原 ACK 回调每次发布包络，消费者收到包络又回 ACK，形成自激重复消息。现在 ACK 回调仅在许可、原因或 epoch 变化时立即发布；正常源更新和定时心跳继续更新时效。负 ACK、最后一方确认和失效撤销不等定时器。
2. **保存每个消费者的撤销时间边界。** 负 ACK 撤销后，旧时间戳和同时间戳的正确认都不能恢复许可；必须收到严格晚于最近负 ACK、仍新鲜且身份相符的正确认。乱序负 ACK 取最大时间，不能降低边界。新提案清空旧 epoch 的确认及边界。

消费者安装恢复可在同一 epoch 完成，但保持取消、过期或几何/附件变化是锁存故障，必须通过新的正式保持和新提案恢复。这两类恢复语义分别验证。

最终实际场次为 `a3_fixed_hold_06.json`。每场先获得六方同版确认，再持续观察正向窗口；撤销后从首个false覆盖到资源释放及下一请求就绪，旧许可均未复活。9场均返回资源已释放，完整记录2641条底盘输出，均为0。已接受的场次没有连续保存里程计速度轨迹；提案准入由协调器检查新鲜停车里程计，因此不能从这些输出样本外推运动停车距离。

实际规划消费者通过所属进程身份和 pidfd 短时暂停，约0.496s后得到 `WAITING_FOR:global_costmap,planner`，同时保持和几何仍有效；恢复进程后同epoch重新确认。局部轮廓故障来自真实代价图的扩大轮廓输入，controller/local_costmap实际产生20条负 ACK，恢复真实轮廓后重新确认。Scene故障由独立回查判为 `PHYSICAL_SCENE_MISMATCH`，随即撤销；世界暂停时ROS时钟确实不推进，失效许可仍被撤销。

延迟字段是本观察窗口中的采样值；续租到期从“停止续租”计时，包含剩余2s资源租约，不等于撤销消息传播耗时。隔离夹具的亚毫秒转变也不能当作实机或运动负载性能。
