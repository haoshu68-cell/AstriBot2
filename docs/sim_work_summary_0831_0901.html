「机器人不动」不是一个故障，是五个独立故障叠加，且其中四个的共同病理是同一条：拿衡量「正常」的量去衡量「失败」。逐个拆开并各自配上能咬住它的测试之后，验收从 16 轮全 FAIL 变为 3 轮全 PASS。

根因

GEN_NEXT_POINT 采到候选 → 计数清零 → VALIDATING 校验失败
  → ++ → 1 → 1<4 → 回 GEN_NEXT_POINT → 又清零 → 永远是 1

找到并消除的一个跨轮次污染源

陈旧 parameter_bridge 在 Gazebo 退出后存活并重连新实例，造成 /clock 双发布者。实测 60 个样本里 2 次 1ms 级时间回跳，足以清空整个 TF buffer 16934 次。表现为 planner 反复 abort、零次到位，而 Gazebo 与 SLAM 看着都正常。

根因是清理模式漏了 /opt/ros/humble 下的二进制（按工作区路径 kill 匹配不到），且 Linux comm 截断 15 字符使 pgrep -x parameter_bridge 永不匹配。

脚本自身踩过的坑（已在脚本内注释固化）

  • comm 截断 15 字符 → pgrep -x 永不匹配
  • awk 匹配到自己 → 需 && $0 !~ /awk/
  • set -u 下 source ROS setup.bash 直接静默退出
  • pkill -f <模式> 命中自己的 shell 命令行 → 循环从中间静默断掉（用 [r]un_... 规避）
  • for c in $(seq …) 里减 c 做重试是无效的 → 改 while

4.3 工具链缺陷

clean_sim_stack.sh 未清理 /dev/shm 里的 Fast DDS 段

实测堆到 138 个，导致新进程报 RTPS_TRANSPORT_SHM Failed init_port … open_and_lock_file failed，三个测量探针全部返回 0 帧。

如果把「0 帧」当成「没有漏点」，会得出三个假的通过结论。本次靠探针里那句「不要把『没数据』当成『干净』」拦住，改走 UDP 传输绕开。脚本本身仍需修——这是最高优先级，因为它会让未来任何一次测量静默产出假结论。
