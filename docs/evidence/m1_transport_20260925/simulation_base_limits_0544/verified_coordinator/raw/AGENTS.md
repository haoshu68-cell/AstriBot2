# 最高项目行为准则

以下规则优先于本项目技能、历史方案及本文件后续章节；系统/开发者指令和用户后续明确要求仍具有更高优先级。

1. **不假设、不隐藏困惑。** 不把未确认的信息当作事实；遇到关键不确定性先核实，无法确定时明确说明。主动说明会影响决策的权衡与取舍。
2. **最小实现。** 只写解决当前问题所必需的代码，不添加推测性功能，不为将来可能的需求预留机制。
3. **最小修改。** 只修改完成当前任务必须改动的地方；只清理自己产生的问题，不顺手重构、整理或覆盖他人的改动。
4. **以验证为完成条件。** 开始前明确定义成功标准，围绕这些标准持续迭代；验证通过前不宣称完成。排查达到一小时仍按下文规则安全暂缓、保留证据并推进独立任务，不能把暂缓或未验证记为通过。

## 反过度工程与反防御性编程

- 信任明确的内部代码契约和框架保证，不重复验证已经保证的条件。
- 输入校验放在系统边界：用户输入、外部 API、网络及设备/传感器输入；内部模块不层层重复校验同一条件。业务状态转换和实际控制约束按其职责实现，不借此增加推测性防御。
- 禁止为已由契约或框架保证排除的“不可能发生”场景添加错误处理、回退、空值检查或验证；若实际证据推翻该保证，再针对真实问题修正。
- 绝不吞掉错误：禁止 `rescue nil`、宽泛捕获后静默继续、以默认值伪装成功。错误必须显式暴露并传播；必要的上下文记录或清理不能掩盖原始失败。
- 禁止为一次性操作创建辅助函数、工具类或抽象。
- 优先快速失败，终止受影响的操作并暴露原因，而不是掩盖问题；已有必要的安全收尾仍须完成。
