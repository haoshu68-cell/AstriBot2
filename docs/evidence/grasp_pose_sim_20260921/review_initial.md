# Initial independent review — 2026-09-21

Scope: read-only review of `astribot_s1_manipulation_perception`, `astribot_perception_msgs`, `astribot_graspnet_runtime`, GraspNet tools, and the pose evaluation boundary. No repository source changes, ROS/Gazebo operations, or GPU inference were performed by the reviewer. Findings below describe the initial source snapshot; they were pending fixes or already being handled by the coordinator when reported. See `review_final_pending.md` for the follow-up status.

No P1 was identified. Initial P2 findings:

1. **FPS equal-distance tie order differs from pinned CUDA.** Initial `tools/vision/graspnet_torch_ops.py:20-32` sorts by numeric lane index, but the CUDA half-step reduction retains the left subtree, producing bit-reversed lane priority. Independently reproduced on CPU: 513 points initially `(0,0,1)`, change index 1 to `(1,0,1)` and index 256 to `(-1,0,1)`; the compatibility implementation returns `[0,1]`, while literal upstream lane/reduction logic returns `[0,256]`. Existing index-512 tie coverage misses this case. Requires regression, corrected operator, new model export and new artifact hashes.
2. **One ordinary nonpositive proposal rejects the complete batch.** Initial `ws_robot/src/astribot_s1_manipulation_perception/src/manipulation_perception_server.cpp:386-389` treats a negative raw score or zero-clamped width as a fatal batch error. Upstream `pred_decode` clamps width to zero and does not constrain the final score to positive values. The coordinator independently reproduced 713 live-input proposals with two negative scores causing complete rejection. Filter these proposals while retaining strict finite-value, rotation and geometry checks, and report counts and empty-batch failure.
3. **Optional visibility metric null aborts successful CAD results.** Initial server line 525 calls `data.value("visible_model_coverage", 0.)`; current CLI `register_cli.cpp:74-75` writes null when no visibility model is configured. Existing null is not a missing field, so nlohmann JSON throws a type error. Initial fixture omitted the field and did not cover the failure. Use an explicit applicability flag and only parse a finite metric when configured.
4. **Overall timeout/cancel does not cover preparation and model hashing.** Initial server lines 352-366 and 338 allocate the full timeout to the child after synchronous preparation; the final elapsed check only rejects afterward. Cancellation cannot interrupt long model hashing. Use one request start/deadline, remaining worker budget, and periodic guards during hashing/preparation.
5. **Pose observations lose task scene/envelope versions.** Initial `ObjectPoseObservation.msg` lacks the scene/envelope fields accepted by `EstimateObjectPose.action`; the observation cannot preserve this snapshot context when stored or forwarded. Add fields and propagate them, rebuilding every interface consumer.
6. **A failed new pose evaluation can reuse an old successful output.** Initial `tools/vision/sim_pose_evaluate.py:16-25` reuses `<scene>.json` and trusts its success without checking process exit status. Reproduce by leaving a prior successful JSON and rerunning the same output directory with a CLI that exits 64/127 without writing a result. The old pose would count toward the new accepted total. Clear output/summary and enforce exit/status agreement.

Positive checks: collision flags are always false; raw model scores above one are preserved and their bounded ranking value is explicitly not a probability; inference remains separate from MTC/IK/execution. Historical failed live reports do not establish fresh Action acceptance. Hardware, VLA and physical grasp validation are explicitly outside this review's requested scope.
