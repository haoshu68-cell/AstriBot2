# 导航前置检查与循环脱困实施方案（已批准施工）

状态：用户已于2026-09-26本轮明确批准按本流程施工；每步先核对闭环，最小实现。当前 front58/domain40 保留，父任务已释放并通过停稳检查，录制已结束；不再发送动作。

## 1. 目标顺序

导航意图 → 获取可用状态 → 判断起点是否被困。

- 起点可用：结束前置处理，启动正常目标路径规划。
- 起点被困：更新机身/机械臂/载荷包络和环境 → 选择安全方向与短动作 → 执行 → 停稳 → 重新获取状态 → 重新判断。
- 数据不可用：等待输入恢复或报警；不把“没有数据”推断为“被困”。
- 无安全候选、没有进展或超出预算：停车并报警，保持任务原因，不启动正常规划。

“进入前置模块”和“执行脱困动作”是两件事。每次导航先经过前置模块；只有判定被困才执行脱困。正常规划的唯一入口是最新一次起点检查通过。

## 3. 数据与职责

### 输入事实

- RobotGeometryState：当前关节状态、机身/机械臂及载荷的分层几何、来源、时效与版本。
- HeightSliceMaps 与原二维代价图：分层环境用于恢复动作扫掠；原导航起点合法性使用其已有二维语义。
- TF/里程计：实际位姿、速度、时间、坐标变换。
- 现有任务与 ArmHold：持物状态、上肢保持、控制权和取消。

诊断读取这些事实，不以“运动已经获得许可”作为读取事实的前提。一个本地评估快照绑定位姿、几何、地图与坐标版本，复用现有消息字段，不新增通用中间平台。

### 控制关系

- 搬运任务：负责 PICK、保持姿态、导航意图、PLACE 和资源生命周期。导航helper完成初次包络绑定后仅监督Nav2目标、取消、反馈和停车，不再复制Nav2内部包络/ACK持续准入。
- 现有 navigation_recovery：负责前置状态机、起点判断、短动作选择、执行后的复检与报警。
- 现有包络协调：确认动作使用的几何版本已经安装；ACK 不表示起点空间可行。
- Nav2 控制端：通过已有唯一命令链执行恢复短动作或正常跟踪，保留取消和实测停车。
- 正常 GridBased/搜索、MPPI、到位调整：本轮不修改算法及碰撞阈值。

恢复规划器使用当前感知、实际包络及位姿一次性检查候选短路径；执行器只跟踪该路径并确认停稳。执行中不再读取包络、ACK、地图或策略约束来重复准入。普通导航继续使用原有检查，不增加第二条速度发布链。

## 4. 状态机

1. WAIT_INPUT：停车并等待可用的包络、环境及定位输入。缺失、过期、尚领先本地时钟等分别给原因。未执行动作时，在有界等待中重新取数。
2. CHECK_START：检查实际当前位置是否满足正常导航的起点准入。
3. SELECT_RECOVERY：仅当起点被困，使用刚更新的分层实际包络与环境评价候选。
4. EXECUTE_STEP：完成本段准入和路径扫掠检查后执行一个短动作，不重复包络、ACK、碰撞及策略准入；保留取消、反馈、速度/距离范围和实测停稳。
5. STOP_AND_RECHECK：确认停止，重新读取实际位姿与环境，再转 CHECK_START。命令执行完不等于已经脱困。
6. READY：最新起点检查通过，结束恢复，才调用正常目标规划。
7. ALARM：无安全动作、持续无进展、输入等待超时或资源故障，保持停车并报告原因。处理完成后从 WAIT_INPUT/CHECK_START 重新进入，不跳到正常规划。

执行段中仅运动反馈失效、执行偏离、取消及执行时限等由控制器终止；感知/包络的新结果留到停稳后的起点复检，不在短段途中重复准入。任务取消结束整个恢复，不自动续跑。恢复次数、总时间/距离使用有界预算；预算耗尽不伪装为起点可用。

## 5. 被困和候选动作的定义

起点判断必须与正常导航的实际起点拒绝条件对齐，复用现有几何判断。它不提前假定一条尚未规划的路径，不强制机器人先原地转向最终目标。

- 二维投影/保守包络导致的起点不可用，但分层实体及扫掠可行：可以执行分层检查通过的恢复动作。
- 实体与可信障碍确实相交，或观测互相冲突：先重新确认；没有证据支持安全运动时报警。首版不提供接触推挤脱困。
- 起点可用但某个后续动作/朝向不可行：属于该动作或路径约束，不能直接等同于当前起点被困。

首版利用底盘已有平移能力，比较后、左、右、前的短动作，保持机身朝向。先剔除未知区域、实体扫掠碰撞、制动空间不足和执行范围之外的候选，再选能增加可用空间或减少阻塞程度的动作；已有净空评价可用则复用，不先引入新优化器。没有安全进展候选就报警。

每次动作不要求直接抵达最终导航目标；动作后更新包络和环境继续判断。避免固定一次后退结束，也避免反复来回移动没有净进展。

## 6. 时效问题与恢复逻辑分别处理

已确认的三个问题并非同一视觉输入一路传递：旧 BT 队列积压、ACK 与本地时钟接收顺序、几何供给间隔超过剩余有效时间。

front58 的执行器实测：sequence=3155，接收 ROS=227.173 s，有效至227.270208102 s，接收 steady=95905.933242999 s，deadline=95906.030451101 s；拒绝时 ROS=227.208 s、steady=95906.043223601 s。因此 ROS 未过期，本地期限超过12.7725 ms。该帧剩余97.2081 ms，邻近观测帧接收间隔约125–133 ms。

源码有100 ms采样节流，启动新工作还依赖20 ms ROS定时器。这与短剩余期限存在供给不匹配，已核实实际产物与源预算：取消100 ms wall节流，保留20 ms ROS采样机会、单个在途计算及完成后发布；隔离测试通过，实场供给间隔仍待重测，未扩大TTL。

特别注意：front58 发生在 PICK/TRANSPORT_POSTURE，尚未交接导航。不能通过把起点检查前移来掩盖上肢执行期间缺少有效几何的问题。诊断入口、恢复动作和必要的上肢执行条件要分别验证。
