## 3. 主线逻辑审查

### 已成立的阶段逻辑

当前正常链是：

```text
任务准入与底盘保持
→ 场景同步、双臂准备、观察目标
→ 规划全部抓取阶段 → 预抓取/接近/闭爪
→ ATTACH_PENDING → 实际附着确认 → ATTACHED
→ 抬升 → 运输姿态 → 包络确认 → 导航
→ 到站保持 → 规划放置及退路 → 接近/放置确认
→ RELEASE_PENDING → 松爪 → 脱离确认 → PLACED
→ 退臂/收臂 → 空载保持阶段 → 独立放稳确认
→ 业务结果完成；资源状态另行确认
```

可保留的正确设计：

- `core.py` 在附着前、松爪前分别写入待确认状态，异常不会直接跳成“已附着/已放置”。
- MTC Place 计划包含释放、解除附着、退臂和收臂，完整计划成功后才返回分阶段结果；释放前已有退路规划。
- 环境变化后重查剩余轨迹，复核等待结束还重新检查 HOLD、底盘及标定条件。不能把旧计划直接继续执行，也不必要求场景永久不变化。
- 取消接受应答与子动作终态分开；native 保持先撤销授权再收集取消和停稳证据，无法证明释放则隔离资源。
- 放置确认包含 PlanningScene 与两次 Gazebo 实际位置观测；视频中的成功不只是收到一个 Action 成功消息。

源代码：[任务阶段](../ws_robot/src/astribot_s1_transport/astribot_s1_transport/core.py)、[MTC](../ws_robot/src/astribot_s1_transport_mtc/src/mtc_planner.cpp)、[ROS 执行适配](../ws_robot/src/astribot_s1_transport/astribot_s1_transport/ros_backend.py)、[原生保持](../ws_robot/src/astribot_s1_transport_native/src/hold_executor.cpp)。
