# RGB-D CUDA 进程恢复与处理健康

当前为候选实现及分层验证记录。完整导航与机械臂主线尚未整体放行；本记录不包含真机、VLA 或完整动态抓取搬运放置验收。

## 任务开始前逻辑复核

按用户新增规则，每项任务开始前依次检查：目标及完成条件、输入输出和真实消费者、控制权和资源所有者、采集/接收/处理时间与版本、拒绝/取消/恢复语义、多场景判据和未覆盖边界。逻辑缺口先进入施工记录，不因列完检查项即认定设计完善。

本项目标是让 GPU 处理阻塞不再阻塞父 ROS 节点的接收、健康发布及正常退出。原始相机健康不代表点云处理可用。处理故障须撤销能力，确认旧 worker 退出后才能启动替代 worker；恢复必须使用故障边界之后的新完整帧。

## 已实施的数据流

```text
RGB-D 接收校验 → 精确时间戳配对缓存（每源最多 4）
  → 一个执行项 + 一个最新待处理项
  → C++ 监督器 → 持久 CPU/CUDA worker（CUDA 默认走独立进程）
  ← 有界本地 IPC 结果
  → 检查请求身份、上下文、采集时间、墙钟、会话与标定
  → 父节点唯一 PointCloud2 发布点

CameraHealth：原始 RGB/深度/内参链
ProjectionHealth：实际处理 backend、worker/processing epoch、采集期限、故障与队列
  → 配置为投影来源的推理服务：两种健康同时有效 + processing_epoch 匹配
  → 启用深度障碍的导航最终保护：头/腹两种健康均有效 + 恢复后新提案/命令
```

CPU 默认实现保留原工作线程。选择 `projection_backend:=cuda` 时，CUDA 初始化、分配、投影和清理在持久子进程中进行。默认设备沿用既有 CUDA 实现的 device 0；该进程隔离不保证设备、显存或计算带宽隔离。

### 进程与协议约束

- 输入最大 32 MiB，输出最大 64 MiB。Unix socket 使用非阻塞父端和有界长度、初始化/处理期限；协议仅用于相同构建版本的本机原生字节序通信。
- 每个请求携带 parent boot nonce、worker epoch、单调 request ID、输入 generation、原始采集时间和预期输出长度。错误身份、截断和超长返回不能发布。
- 默认初始化期限 3 秒、单次处理期限 200 毫秒、TERM 回收窗口 50 毫秒、KILL 回收窗口 100 毫秒、重启退避 100 毫秒、最多 3 次重启。初始化完成不延长原始帧 250 毫秒期限。
- 使用 pidfd 或尚未回收的直接子进程身份控制 worker。回收使用非阻塞查询；未确认退出进入 `QUARANTINED`，不把“发出 KILL”视为已释放。
- 取消唤醒 IPC 等待，节点退出先取消 projector，再等待工作线程。测试验证本实现路径的完整墙钟范围，不声称对操作系统任意调度延迟提供硬实时保证。

### 健康与恢复约束

`ProjectionHealth` 的周期发布不更新旧采集期限。采集时间、首次有效采集时间和最后发布时间均单独记录。ROS 时间与单调墙钟任一超预算即无效；输入故障、会话/标定变化和时钟回退使旧工作失效。

CPU 回退通过 `allow_cpu_fallback` 显式开启，默认关闭。开启后也须确认旧 GPU worker 退出，单独递增处理版本并清空排队帧，再等待新完整帧；回退期间保留相同精度和 250 毫秒预算。状态显示实际 `cpu` backend 和 `READY_CPU_FALLBACK`，本次节点生命周期内不自动切回 CUDA。

推理服务的 `projection_health_topic` 为空时，输入为独立外部快照模式。配置为 `/perception/projection_health/<camera_id>` 后，抓取和物体姿态请求须携带对应 `processing_epoch`；缺失、过期、错误版本和推理中途换版均拒绝或撤销。新 Action 字段改变接口格式，客户端和服务端必须使用同一消息版本。本候选采用独立消息安装，未覆盖共享安装。

### 导航最终执行保护

在既有、唯一发布 `/cmd_vel` 的 C++ `final_protection_cpp` 中增加只读启动配置 `required_projection_cameras`。标准导航启动在 `enable_depth_obstacles=true` 时要求 `head_rgbd` 和 `torso_rgbd`；关闭深度障碍时使用空列表，保留旧模式。腕部相机不成为全局导航的无条件依赖。

每个必要源同时检查原始健康和处理健康，核对相机身份、光学 frame、ROS 采集龄期、失效时间、单调墙钟接收龄期及采集推进。重复心跳不能延长同一采集的墙钟期限。原始/处理 epoch 或 frame 变化、短暂故障与时钟回退都会锁存；恢复必须使用故障边界之后的新采集。故障和恢复都会清除旧速度与策略提案，恢复后的提案时间必须晚于放行边界。

该检查叠加于原有激光覆盖、连续扫掠、包络版本、区域约束、命令期限和制动限制，不能替代它们。无时间戳的上游 `Twist` 仍沿用接收时间语义，不声明新增了发送端任务事务身份。高层任务接口可以先接受任务再进入保持；本项不是整机统一任务准入总线。

### 审查后修正

1. 时钟回退可能先被原始健康回调或请求检查观察到，导致处理健康缓存保留旧时间。统一三个入口的回退处理，覆盖两种回调顺序。
2. 健康定时器可能先报旧输出过期，再发生 CPU 回退。实际 backend 切换须再次建立版本/采集边界，否则会处理切换前排队帧。新增测试复现了错误发布，再修复。
3. 仓库导航中 `/clock` 与处理健康到达顺序不同，出现健康 header 比保护节点时间快 1 ms 的记录。原接入逻辑误撤销了仍有效的旧健康缓存。纯 C++ 测试复现后改为丢弃同版本未来心跳，既不采用未来数据，也不延长旧采集/墙钟期限；明确故障或版本变化仍立即撤销。额外计数 `projection_future_samples_rejected` 可观测该路径。
4. 顺链复核推理服务，原始和处理健康回调都会以未来心跳覆盖有效缓存。两个 Action 反例复现错误拒绝后采用相同的丢弃语义，并验证未来无效消息仍撤销、反复未来心跳不能续期。最终推理服务 3 个 CTest、37 个 GTest 用例通过；该补充是 C++ 服务/隔离 ROS 证据。

上述修正均保留失败测试和修复后的相关回归结果，见本项 evidence 目录。仓库导航首轮发现非注入窗口的额外撤销，记为 FAIL；后续加强判据，除低频诊断外，同时核验保护版本跳变和 20 ms 约束流，避免遗漏短暂故障。
