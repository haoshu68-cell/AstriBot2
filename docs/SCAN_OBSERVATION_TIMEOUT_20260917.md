# 扫描观测更新超时修复与仿真验证

日期：2026-09-17。范围：Nav2 障碍层扫描更新超时，Gazebo + RViz，MPPI、策略 OFF、0.35 m/s。没有连接或部署真机。

## 修改与判断

MPPI、RPP 配置的 local/global costmap 中，四处 `obstacle_layer.scan.expected_update_rate` 从 **0.2 秒改为 0.3 秒**，补充单位注释。没有关闭断流检查。

稳定扫描实测约 10 Hz，修复前最大接收间隔 109 ms，修复后 113 ms。原值对正常扫描够用，但一次丢帧叠加传输/TF 处理抖动可能超过 200 ms。新值提供一个扫描周期的额外余量，与现有策略配置的 0.3 s 传感器预算一致；它不修复上游断流、TF 缺失或旧消息重发。

局部地图更新 5 Hz、全局地图更新 1 Hz、控制频率、足迹、膨胀、规划与跟踪算法均保持原值。到位验收保持当前仿真档 **2 mm / 0.1°**。控制库、启动脚本及统计脚本已保存哈希，源码配置的结构化差异仅上述四项。两版路线记录的到位控制参数一致。

原栈日志和本次正常运动基线均未发现扫描观测超时，故不能把历史停车直接归因于该参数。本次修复针对受控复现的短时更新间隔退化。

## 同源地图对照

使用本机 Nav2 的四个真实 `Costmap2DROS` 实例，分别加载局部/全局地图及 0.2/0.3 s 阈值。它们同时订阅同一份 Gazebo 扫描，经独立验证话题注入更新间隔变化，保留原始扫描时间戳。此探针不发布运动指令，以下次数是地图失效切换，不是机器人停车次数。

最终完整运行正常退出，结果如下：

| 场景 | 0.2 s | 0.3 s |
|---|---:|---:|
| 正常约 10 Hz，地图失效切换 | 两图均 0 | 两图均 0 |
| 240～260 ms 更新间隔，累计 48 s，局部地图失效切换 | 47 次，累计 9.266 s | 0 次 |
| 同一抖动输入，全局地图失效切换 | 3 次，累计 4.839 s | 0 次 |
| 两次各 2 s 的断流 | 两图均检出 2/2 | 两图均检出 2/2 |
| 三段恢复窗口末尾持续 0.5 s | 两图均有效 | 两图均有效 |

候选局部地图从最后一次扫描发布到检出失效为 0.353～0.394 s，全局为 0.454～1.198 s。阈值增加了 100 ms 容忍量，实际检出还受地图更新周期、处理和检查相位影响；这些数字不是车辆刹停时间或刹停距离。没有增加地图更新频率来掩盖这一差别。

验证工具首次退出漏做生命周期清理；补齐后又定位到组合节点销毁时插件库早于 callback-group 弱引用卸载。工具现显式清理生命周期，并保留库引用直到组合节点全部销毁。退出检查和最终完整重跑均为 0；前两次记录另存，不作为最终验收结果。工具仅保存在仓库外证据目录。

本次证明：短时扫描抖动的失效敏感性降低，持续断流仍能检出，MPPI 的本次两组运动与原到点精度验收通过。RPP 两张代价地图配置与 MPPI 完全一致且构建/静态检查通过，但没有另做 RPP 运动闭环。没有完成新的全场景窄通道回归或真机验收。
