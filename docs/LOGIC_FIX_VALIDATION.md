# 逻辑修复验证记录

验证日期：2026-09-13。修复范围见 [LOGIC_REVIEW.md](LOGIC_REVIEW.md)。
比较基线是上一轮“保留原逻辑”的最终工作区，而非 Git HEAD；此前的清理及用户已有改动均保留。
备份与本轮临时证据目录：`/tmp/astribot_logic_fixes`。此目录不是长期归档，关键结果记录于本文。

## 核心功能保持

- 两份 MPPI/RPP YAML 与本轮修复前逐字相同，三阶段核心参数未调整。
- path_tracking 的 12 个 C++ 源码/头文件中，只有 ThreePhaseController 增加相位坐标变换。剔除这一修复后与备份逐字一致。
- 内层规划、控制策略、速度曲线、惯性补偿、多源到位控制、3 cm/1.5° 判据及异常预算保持。
- max_linear_speed 仍是各轴上限；smoother 现在兑现该参数，不提高 YAML 中原本更严格的上限。

- 12 个自研 ROS 包构建通过；保留已有 description 包 CMake CMP0009 开发警告。
- 54 项相位/惯性/接近控制回归通过。
- 17 项到位及坐标变换回归通过，包含 nav2_pose、slam_pose、vision、mark、错误数据、超时与撤销成功状态。
- 规划器等价检查通过：三组含障碍场景保持原生 Smac 路径，只有精确终点处理允许改变末点。
- 6 组 Python 故障回归在旧版均失败，修复后均通过；新增 deskew 动态参数拒绝、陈旧姿态不误锁死、空闲看门狗不干扰其他输入检查通过，共 9 组。
- 非恒等 map→odom 回归使用旧库失败、新库通过；同一物理位姿旋转输出一致，丢失 TF 时拒绝计算。

- 28 项配置/脚本检查通过：两控制器三档速度、地图话题/QoS、RViz 两环境时钟、SDK 两种布局、shell 特殊字符安全往返及 YAML 保持。

## 运行与边界

初次 MPPI 运行 Gazebo 有 21 个 transport 话题，物理持续步进；6 秒收到 clock=5897、odom=299、scan=63，TF 龄期约 0.02 秒。
运行实例的 smoother 上下限为 ±[0.5,0.5,2.0]，ArrivalController/ExactGoalPlanner 均已实际加载。

RPP 首次尝试停在 controller_server 激活阶段，未计入导航通过记录。没有把生命周期卡住当成控制算法故障；本轮未修改 Nav2/DDS 启动机制。

SLAM/视觉/Mark 只完成消息、误差计算及失效分支回归，尚未验证真实传感器噪声和外参。实机脚本只做离线验证，未连接硬件下发运动。
点云 deskew 原本没有实现，本轮明确拒绝伪启用，不声称增加了逐点运动补偿。
